# Agentic Optimization Refactor Plan

## 1. Core Motivation

The refactor should not be constrained by the old prototype implementation
shape. The previous framework had useful lessons, especially around fresh Codex
sessions, workspaces, attempts, reusable findings, tools, traces, verification
feedback, and web visibility. Those are implementation references, not
preservation requirements. The filesystem RPC / evaluator socket architecture
has been retired from the active source tree and should not define future work.
The target is a general autonomous optimization framework: one that can cover
ML/model optimization, coding benchmarks, numerical search, data generation, and
other domains through task contracts rather than framework rewrites. The system
should be split into two explicit planes:

1. Server / control plane
2. Worker node / autonomous agent plane

The server owns experiment order, official state, queues, resource policy,
evaluation integrity, and durable artifacts. The worker node owns autonomous
research behavior: reading prior work, deciding what to try, writing code,
running local checks, requesting jobs/evaluations, updating notebook state, and
sharing findings.

The design goal is:

```text
Server controls truth, resources, queues, evaluation, and persistence.
Worker controls research behavior, implementation, debugging, and iteration.
Task controls domain contract, public/hidden data boundary, metrics, and runtime.
Providers control concrete compute/logging/storage integrations.
Skills control agent behavior style, not infrastructure safety.
Storage keeps artifacts durable, but should not define the architecture.
```

The system in `safety-research/automated-w2s-research` is a useful starting
reference for the server-side shape: experiment queue, web dashboard, worker
dispatch, RunPod/S3 orchestration, server-side evaluation, findings, snapshots,
and leaderboard. We should reference that control-plane design, but not inherit
its benchmark-specific assumptions. This framework must stay task-general.

The system in `huggingface/ml-intern` is a useful reference for ML ecosystem
integration and product-grade tool operation: remote training jobs, training
telemetry, sandboxed tool execution, approvals, cost estimation, event streaming,
and session traces. We should reference those capabilities as provider/tool
adapters and policy patterns, but not inherit a session-centric architecture as
the primary control plane. HF Jobs and Trackio are examples of these concepts,
not preferred defaults for this framework.

The combined target is:

```text
automated-w2s-research style control plane
  + ml-intern style ML tool/provider ecosystem
  + task-general contracts
  + disposable autonomous coding workers
  = general autonomous optimization framework
```

## 2. Non-Goals

- Do not rebuild a benchmark-specific framework.
- Do not encode a fixed numbered workflow into the server, prompts, or skills.
- Do not make the server choose concrete research ideas for the agent.
- Do not make filesystem paths the primary user-facing architecture.
- Do not preserve or reintroduce the retired `fsd`, `fs_cli`, `ve`, or
  filesystem-RPC/evaluator-socket architecture.
- Do not let task-specific ML conventions, benchmark metrics, training stacks,
  or private evaluator data layouts become framework constants.
- Do not make chat sessions the primary unit of global state. Sessions are one
  worker runtime, not the framework architecture.
- Do not treat RunPod, MLflow, S3, Docker, HF Jobs, Trackio, or any other
  provider as a privileged built-in path. They are provider adapters behind
  common interfaces. RunPod and MLflow can be first implementation targets
  without becoming architectural constants.
- Do not require Codex forever. Codex is the first worker backend, not the
  architecture.

## 3. Two-Plane Architecture

### 3.1 Server / Control Plane

The server is the authoritative owner of global state. It should provide a
semantic API over durable storage instead of exposing raw archive structure as
the main abstraction.

Primary server responsibilities:

```text
Task registry:
  Load task packages.
  Expose task metadata, public context, candidate contract, runtime requirements,
  evaluation protocol, artifact policy, and resource hints.

Experiment manager:
  Create experiments from task + configuration.
  Track status, budgets, assignments, stop reasons, and progress.
  Store experiment-level policy and metadata.

Queue / scheduler:
  Maintain queued, assigned, running, completed, failed, cancelled states.
  Enforce concurrency, resource budgets, retries, timeouts, and cancellation.

Worker assignment service:
  Create worker assignments.
  Attach task, direction/island, agent type, public context, visible history
  policy, budget slice, and workspace seed.
  Never prescribe the exact inner-loop workflow.

Job service:
  Launch, monitor, attach to, and cancel jobs.
  Support local subprocess, local Docker/GPU, RunPod, AWS, Slurm, HF Jobs,
  SkyPilot, Modal, or other providers behind one interface.
  Track logs, resource usage, cost estimates, completion state, and artifacts.

Telemetry service:
  Record training/process metrics, curves, structured logs, and dashboard links.
  Support MLflow first, with TensorBoard, W&B, Trackio, plain JSONL logs, and
  task-specific dashboards as later provider adapters.
  Never replace official server-side evaluation.

Evaluation service:
  Own hidden evaluator internals and official metrics.
  Accept task-defined candidates, artifacts, or output bundles.
  Return public-safe feedback.
  Update official results and leaderboard only through server-side evaluation.

Artifact registry:
  Track attempts, snapshots, datasets, task output artifacts, checkpoints, logs,
  metrics, traces, and visualizations.
  Store metadata in the server and large blobs in a pluggable object store.

Collaboration store:
  Store findings, shared tools, notebook checkpoints, snapshots, result
  summaries, and leaderboard entries.
  Historical "patterns" are finding records, not a separate resource type.
  Provide search and filtered materialization for workers.

Policy layer:
  Enforce budget, cost, approval, secrets, data visibility, artifact retention,
  and anti-cheating rules.
```

The control plane is allowed to schedule and stop work. It is not allowed to
decide which concrete idea the agent should try next.

### 3.2 Worker Node / Autonomous Agent Plane

A worker node is an execution environment where a coding agent runs. It should
be disposable. It may have a local workspace, but it must not be the owner of
official experiment state.

Primary worker responsibilities:

```text
Autonomous research:
  Inspect public context, prior findings, attempts, leaderboard, snapshots, and
  task knowledge.
  Decide what hypothesis or implementation path to pursue.
  Write and modify candidate code.
  Run local checks and small validations when useful.
  Request longer jobs or official evaluation when useful.
  Diagnose failures and pivot autonomously.

Notebook and local memory:
  Maintain local scratch state.
  Checkpoint notebook/worklog state to the server.
  Record what was tried, what failed, and what should be reused.

Artifact production:
  Produce code diffs, candidate snapshots, task outputs, logs, metrics, analysis
  scripts, plots, and findings.

Collaboration:
  Share useful findings and tools.
  Read/download snapshots and findings from other workers.
```

The worker should see capabilities, not global secrets or hidden evaluator
internals. For example, a worker can call an evaluation tool, but it should not
read private scoring data or private grader code.

## 4. Worker Autonomy Principle

The common lifecycle is useful as a mental model:

```text
1. User/config creates task + experiment
2. Server generates worker assignment
3. Server creates or schedules worker node
4. Worker pulls public context, prior findings, leaderboard, snapshots
5. Coding agent autonomously implements ideas
6. Worker performs small validation
7. Worker asks server/job service to launch formal training or evaluation jobs
8. Job produces task outputs/logs/artifacts
9. Worker or job submits outputs to server evaluator
10. Server computes official metrics and updates leaderboard
11. Agent shares finding and server creates snapshot
12. Other workers reuse findings/snapshots
```

But steps 4-9 must not become a required sequence. For the worker, these are
available actions, not a workflow. An autonomous worker may:

- read context many times or not at all after startup
- implement several ideas before any evaluation
- run many small validations, one validation, or none if the task does not need it
- launch multiple jobs, attach to existing jobs, cancel jobs, or only run local
  checks
- submit outputs before sharing a finding, or share a hypothesis before any
  official result
- inspect failures and repeat diagnosis many times
- checkout a snapshot in the middle of a run
- abandon a direction after evidence shows it is unpromising

The server should enforce boundaries and budgets, not workflow order.

## 5. General Object Model

The refactor should introduce explicit objects. The old filesystem layout should
not remain the architecture or the default backend. It can be mined for import
logic, reproducibility export formats, or compatibility shims only when those
uses are worth the maintenance cost.

```text
Task:
  Domain package, public context, hidden evaluator, candidate contract, runtime
  spec, metrics, artifact policy, and default research directions.

Experiment:
  A configured optimization run for one task.
  Owns budgets, worker assignments, queue state, leaderboard scope, and policy.

WorkerAssignment:
  A unit of autonomous work.
  Includes task id, experiment id, direction/island, agent type, visible context
  policy, budget slice, and initial workspace seed.

WorkerSession:
  One concrete agent execution attached to an assignment.
  May be local, Docker, cloud, or another backend.

Environment:
  Server-owned runtime environment prepared from framework or task specs.
  Current default provider is local_venv; docker_image is the next provider gap.

EnvironmentOverlay:
  Worker-requested dependency extension layered on a base environment under
  experiment policy. It must not mutate the task base environment.

Attempt:
  A candidate artifact snapshot or code state produced by a worker.
  May link to jobs, evaluations, findings, traces, and notebook checkpoints.

Job:
  A durable compute task launched by the server.
  Tracks provider, status, logs, resource usage, cost, inputs, outputs, and
  artifacts.

TelemetryRun:
  Non-official observability record for a job or attempt.
  Tracks provider, dashboard URL, metric streams, summaries, logs, and linked
  artifacts.

Evaluation:
  Server-side official or diagnostic scoring result.
  Links to attempt/artifact/job and returns public-safe metrics.

LeaderboardEntry:
  Server-owned official score publication. The highest active row in a scope is
  the derived incumbent.

Artifact:
  Any durable object: code snapshot, model, checkpoint, task output file, dataset
  slice, log bundle, metric curve, plot, trace, or result manifest.

Finding:
  Agent-authored reusable knowledge.
  Can be result, hypothesis, insight, error, or task-defined subtype.

NotebookCheckpoint:
  Worker-authored local memory checkpoint.
  Replaces the idea that one workspace file is the only continuity mechanism.

Policy / Budget / Approval:
  Experiment and session constraints for evaluator runs, GPU hours, dollar cost,
  storage, secrets, network, and provider actions.
```

## 6. Server-Worker Protocol

The important refactor is the protocol boundary. The worker should interact with
the server through semantic operations.

Target worker-to-server operation family. The current CLI implements this
through context, artifact, evaluation, job, environment, finding, notebook, and
telemetry tools; a dedicated `Attempt` resource and some convenience operations
such as job attach/budget status are still future work.

```text
request_context
search_findings
get_leaderboard
get_incumbent
checkout_incumbent
upload_artifact
create_attempt
launch_job
attach_job
cancel_job
read_job_logs
submit_for_evaluation
share_finding
checkpoint_notebook
request_environment
request_environment_overlay
record_telemetry
report_failure
request_budget_status
```

Server-to-worker information:

```text
assigned_task
assigned_direction_or_island
agent_type
public_context_manifest
visible_history_policy
workspace_seed
budget_status
job_status
evaluation_result
approval_required
stop_signal
```

The current implementation exposes this through CLI tools inside the workspace.
These tools call the server API directly and are not compatibility wrappers
around the retired prototype command surfaces:

```text
ctx        read public context, task contract, findings, evaluations, jobs,
           environments, leaderboard, incumbent, telemetry, artifacts, and
           notebook checkpoints
artifact   upload/list artifacts and checkout the current incumbent candidate
eval       verify/probe/submit candidates or artifacts
finding    share/search findings
notebook   checkpoint/list worker notebook state
job        launch/status/logs/wait/cancel compute jobs
env        inspect task environments and request dependency overlays
telemetry  start/log-metrics/status/list/finish non-official metric runs
```

The exact command names are less important than the boundary: worker-facing
commands should describe research operations, not raw archive traversal.

## 7. Storage Model

Filesystem export can remain valuable, but it should be demoted from "the
architecture" to an optional export/import format. The default storage path
should be server-owned semantic state plus a local or remote artifact store.

Recommended storage split:

```text
Server database:
  Resource metadata, status, indexes, queue state, assignment state, leaderboard,
  approval state, and artifact manifests.

Filesystem export:
  Optional reproducibility bundles, debug bundles, and human-inspectable
  snapshots generated from server-owned state.

Object store:
  Large artifacts such as checkpoints, models, datasets, task outputs, metric
  histories, and compressed snapshots.
```

The web DB should no longer be an index/cache over raw filesystem concepts. In
the new architecture, the server owns semantic state. Filesystem exports are
derived artifacts, not a dependency the worker or server must preserve.

## 8. Task Contract

A task should declare what a worker can see, what it can produce, and how the
server evaluates it. The framework should avoid baking in ML-specific or
benchmark-specific rules.

Generic task fields:

```text
public_context:
  Documentation, public data, baseline summaries, starter code, task knowledge,
  allowed APIs, and visible prior artifacts.

hidden_context:
  Evaluator internals, private scoring data, private test cases, private
  reference outputs, and any task-owned secrets.

candidate_contract:
  What the worker is expected to modify or produce.
  Examples: code entrypoint, output artifact, generated file, configuration,
  dataset transformation, solver harness.

validation_contract:
  Cheap structural checks or smoke tests.

probe_contract:
  Optional diagnostic feedback surface.

evaluation_contract:
  Official scoring interface and public-safe result schema.

metrics_policy:
  Score, secondary metrics, statistical validity rules, repeatability rules,
  leaderboard eligibility, and anti-cherry-picking rules.

runtime_policy:
  Python/container requirements, hardware hints, dependency locks, preflight
  checks, allowed network, and job provider constraints.

artifact_policy:
  Which artifacts are preserved, hidden, public, large, retained, or excluded
  from snapshots.
```

For ML tasks, this can express train/predict/evaluate. For coding benchmark
tasks, it can express verify/probe/submit. For search or numerical tasks, it can
express candidate functions and hidden scoring. The framework should not care
which domain it is.

## 9. Reference Systems: What To Borrow

The two external references are complementary. `automated-w2s-research` is
experiment-centric. It has the stronger control-plane architecture, but it is
specialized to one benchmark. `ml-intern` is session-centric. It has the
stronger ML operations/tooling layer, but it does not provide a task-general
experiment/evaluator/leaderboard loop.

The refactor should combine the useful parts without copying either system's
core assumption.

### 9.1 From automated-w2s-research

Borrow server-side design ideas:

- Web-backed experiment creation.
- Queue and worker dispatch.
- Local/Docker/cloud execution modes.
- RunPod/S3 orchestration pattern.
- Worker entrypoint that downloads inputs and uploads final artifacts.
- Server-side evaluation endpoint that owns hidden data.
- Findings and leaderboard publication.
- Snapshot creation and reuse.
- Completion signal via durable result artifact.

Do not borrow task-specific assumptions:

- Benchmark-specific data layout.
- Benchmark-specific data isolation mechanics as framework concepts.
- Task-specific training stacks as built-in requirements.
- Task-specific repeat counts as framework constants.
- Task-specific metrics as framework metrics.
- Task-specific module naming conventions as global candidate contracts.

The right abstraction is:

```text
automated-w2s-research server design -> general experiment server
automated-w2s-research worker protocol -> one possible task/worker contract
automated-w2s-research benchmark logic -> task package only
```

### 9.2 From ml-intern

Borrow ML operations and product-system ideas:

- Remote training jobs as provider-managed compute.
- Training telemetry as provider-managed observability.
- Sandbox/local tool execution as one worker-local execution provider.
- Cost estimation before expensive provider actions.
- Approval gates for destructive, long-running, or expensive operations.
- Optional YOLO/auto-approval mode with hard budget caps.
- Streaming job logs and tool events.
- Session trace persistence for debugging and audit.
- HF ecosystem integrations for datasets, models, Spaces, Hub repos, and docs.

For the first implementation target, prefer:

- RunPod as the first cloud `JobProvider`.
- MLflow as the first training `TelemetryProvider`.

Keep HF Jobs and Trackio as later optional adapters, not near-term dependencies.

Do not borrow session-centric assumptions:

- A chat/session should not be the global owner of an optimization run.
- A tool call should not be the only durable representation of a long-running
  job.
- MLflow/Trackio/TensorBoard/W&B metrics should not replace official
  server-side evaluation.
- HF Hub artifacts should not replace the framework artifact registry.
- Session traces should not replace attempts, findings, snapshots, or notebook
  checkpoints.
- Approval UI should not define policy; policy should live in the server.

The right abstraction is:

```text
ml-intern HF Jobs tool -> optional JobProvider adapter
ml-intern Trackio integration -> optional TelemetryProvider adapter
ml-intern sandbox tools -> WorkerExecutionProvider adapter
ml-intern approval/cost logic -> server policy and budget layer
ml-intern session traces -> worker-session audit artifacts
ml-intern product UI -> optional product UX ideas
```

### 9.3 Combined Architecture Rule

The server should be experiment-centric. Worker sessions should be disposable.
Provider tools should be pluggable. Official evaluation should remain
server-owned.

This means an ML task may use RunPod for training, MLflow for live metrics, S3
for large artifacts, and a hidden server evaluator for official scoring, all in
the same experiment. Another deployment may swap RunPod for HF Jobs or AWS, or
MLflow for Trackio or W&B, without changing the task or evaluation contract.
None of those providers should be required for a simple coding or numerical
optimization task.

## 10. Job and Evaluation Semantics

The new `EvaluationService` should provide durable synchronous and asynchronous
evaluation. It can reuse task evaluator code where useful, but it should be
implemented as a server-owned resource service rather than a socket CLI.

Desired semantics:

```text
Worker creates attempt or artifact.
Worker asks server to evaluate or launch job.
Server records evaluation/job resource.
Worker can detach.
Another fresh worker session can attach later.
Server records final public-safe result.
Leaderboard updates only through official server-side evaluation.
```

This is essential for long-running ML training. A single autonomous turn should
not need to remain alive for a multi-hour training job. Fresh sessions should be
able to resume by querying durable job/evaluation state.

## 11. Findings, Tools, and Notebooks

The ideas behind `WORKLOG.md`, patterns, and shared tools remain useful, but
they should be generalized into server-owned resources. `Pattern` should not be
a separate durable resource. It is the old name for a reusable `Finding`, or at
most a `finding_type` such as `pattern`, `insight`, `result`, `hypothesis`, or
`error`.

```text
Notebook:
  Worker-local scratch memory.
  Checkpointed to server.
  Restored or summarized into later sessions.

Finding:
  Server-visible reusable claim or observation.
  Can link to attempts, jobs, evaluations, artifacts, and snapshots.
  Covers the role previously called pattern.

Shared tool:
  Executable helper artifact.
  Indexed by server and materialized into worker workspaces on demand.
```

The server should support negative findings and failure reports. In autonomous
research, failed runs are often more valuable than raw logs.

## 12. Policy, Secrets, and Isolation

This layer must be server-owned.

The server should enforce:

- hidden data isolation
- evaluator isolation
- worker-visible public context only
- provider secret injection without secret disclosure
- budget and approval policy
- resource limits
- artifact retention
- snapshot visibility
- safe logging and secret scrubbing

Skills may remind the agent how to behave, but skills must not be the security
boundary.

## 14. Migration Strategy

This should be a large refactor, but it can be staged.

Stage 1: Design skeleton

- Define the new object model and protocol.
- Define Task, Experiment, Assignment, Attempt, Job, Evaluation, Artifact,
  Finding, and NotebookCheckpoint as server-owned resources.
- Document any old resource mappings only as one-way migration/import notes, not
  as compatibility requirements.
- Build the new control-plane model as server-owned state, not as wrappers over
  the previous prototype services.
- Remove the previous prototype service packages from the active source tree.
  Reuse implementation ideas only when they improve the new design.
- Status: complete for the current baseline. The resource dataclasses,
  repository tables, task contract boundary, and active source layout exist.

Stage 2: Server-first local mode

- Make the web/backend service the owner of experiment and assignment state.
- Launch Codex workers through server-owned worker assignments.
- Keep the useful fresh-session behavior, but make sessions attach to assignment
  resources and use server APIs for durable state.
- Store notebook checkpoints and worker events through server APIs.
- Do not require worker sessions to read or write the old run filesystem layout.
- Status: complete for local semantic-worker operation. The web/control-plane
  service owns experiment, assignment, session, event, notebook, artifact, job,
  and evaluation state.

Stage 3: Semantic worker tools

- Add worker-facing tools for context, findings, artifacts, evaluation, jobs,
  and notebook checkpoints.
- Prefer semantic server tools over low-level archive command shapes.
- Make the semantic tools call the server API directly. `ctx`, `eval`,
  `artifact`, `finding`, `notebook`, `job`, `env`, and `telemetry` are
  first-class worker tools, not compatibility wrappers around the retired
  prototype tools.
- Preserve reproducibility through explicit export commands generated from
  server-owned resources, not by depending on the old filesystem layout.
- Status: complete for the current semantic tool surface. Worker workspaces
  expose `ctx`, `artifact`, `eval`, `finding`, `notebook`, `job`, `env`, and
  `telemetry`; no `fs` or `ve` wrappers should be materialized.

Stage 4: Artifact registry

- Introduce artifact manifests.
- Add local object-store support first.
- Move large artifacts out of snapshots.
- Add artifact links to attempts, jobs, evaluations, findings, and traces.
- Current implementation checkpoint: local object-store artifact registration is
  implemented through the control-plane service. Registered path artifacts now
  produce manifest files with digest, content path, size, file count, source
  path, and metadata, and evaluation can use an `artifact_id` as input.
- Status: complete for local object-store semantics and first S3-compatible
  upload adapter. Remaining work belongs to richer retention policy,
  downloads/materialization, and production hardening.

Stage 5: Job service

- Implement local subprocess and local Docker provider first.
- Add durable job status, logs, cancellation, attach, and completion records.
- Add budget and approval gates.
- Then implement RunPod as the first cloud `JobProvider`, adapting RunPod/S3
  orchestration ideas from `automated-w2s-research`.
- Keep HF Jobs as a later optional provider adapter rather than a special worker
  tool.
- Current implementation checkpoint: the first server-owned `JobService`
  supports local subprocess jobs and a local Docker adapter with durable `Job`
  records, job directories, command manifests, stdout/stderr logs, status
  lookup, log reads, cancellation, basic approval/cost/max-job gates, and a
  RunPod provider with dry-run support and retryable capacity-error
  classification.
- Status: complete for local subprocess, local Docker, and first RunPod provider
  shape. Cloud execution still needs production S3 workspace orchestration and
  real deployment testing.

Stage 6: Async evaluation

- Build a new server-side `EvaluationService` that supports both synchronous
  cheap checks and asynchronous long evaluations.
- Reuse existing task evaluator functions only as task-level implementation
  details; evaluation architecture belongs in the server-owned service layer,
  not in a worker transport or CLI.
- Support artifact/candidate submission, hidden evaluator state, and
  public-safe result records.
- Current implementation checkpoint: evaluation is now a server-owned
  `Evaluation` resource implemented by a dedicated server-side
  `EvaluationService`. `verify` and `probe` default to synchronous checks,
  `submit` defaults to asynchronous execution via `JobService`, and evaluations
  can be requested with `entry_path` or `artifact_id`. The previous evaluator
  service package has been removed from the active source tree.
- Status: complete for server-owned async evaluation and artifact/candidate
  input. Future work should improve evaluator isolation, task-specific result
  schemas, and hidden-state handling, not recreate a separate evaluator
  CLI/service architecture.

Stage 7: Telemetry provider

- Add a telemetry abstraction for non-official training/process metrics.
- Implement MLflow first.
- Store telemetry run metadata, dashboard URLs, metric summaries, and exported
  metric artifacts in the server/artifact registry.
- Keep telemetry separate from official evaluation and leaderboard updates.
- Status: complete for first implementation. `TelemetryRun` is a server-owned
  resource with local JSONL metric export and an optional MLflow provider
  adapter. Telemetry is exposed through API routes and the worker `telemetry`
  tool, and remains separate from official evaluation.

Environment control checkpoint:

- Task runtime dependencies are now represented as server-owned environments
  rather than ad hoc interpreter assumptions.
- Current implementation uses `EnvironmentService` with a `local_venv` default
  provider, durable `Environment` and `EnvironmentOverlay` records, task base
  environment preparation, evaluation environment metadata, and the worker
  `env` tool.
- Workers request extra dependencies through overlays instead of mutating the
  task base environment. `verify` and `probe` can use approved overlays; official
  `submit` currently resolves through the task base environment.
- Remaining gap: add the `docker_image` provider behind the same resource model
  for stronger reproducibility and isolation.

Stage 8: Convert tasks

- Convert existing tasks onto the new Task/Experiment/Assignment model.
- Keep simple tasks simple.
- Remove direct task dependence on old archive paths where possible.
- Add one ML-style task to validate train/predict/evaluate, artifact registry,
  job service, MLflow telemetry, and hidden evaluator isolation.
- Status: partially started. `tasks/circle_packing_26` is the current converted
  benchmark task and exercises task runtime specs, environment preparation,
  verify/probe/submit, candidate snapshots, leaderboard/incumbent, and research
  direction assignment. Broad task migration and the first ML-style task remain
  pending.

Stage 9: Cloud execution

- Add RunPod provider.
- Add S3 or S3-compatible object store provider.
- Later add AWS/Slurm/SkyPilot/Modal as provider adapters.
- Later add provider-specific telemetry integrations such as Trackio, W&B, or
  TensorBoard import without making telemetry the official evaluator.
- Status: complete for first provider adapters. RunPod has a `JobProvider`
  adapter with dry-run support and S3-compatible artifact upload exists behind
  the artifact registry. Remaining work is production orchestration:
  workspace/data upload bundles, pod entrypoints, result polling, retries, and
  cleanup policies.

Stage 10: Policy and product layer

- Add cost estimation for provider jobs.
- Add approval gates for expensive, destructive, secret-bearing, or
  long-running actions.
- Add optional auto-approval modes with hard experiment/session budget caps.
- Add event streaming and trace views for debugging worker sessions.
- Status: complete for first implementation. Job policy now supports approval
  requirements, auto-approval with hard cost caps, per-job and total estimated
  cost caps, and max-job caps. The API exposes event listing, SSE event
  streaming, and session trace JSON. Full secrets management, richer budget
  accounting, notification integrations, and product UX remain future work.

## 15. Success Criteria

The refactor is successful if:

- The same server can run non-ML coding tasks, numerical optimization tasks, and
  ML training tasks.
- Worker sessions are disposable and resumable.
- The worker has no direct access to official hidden evaluator internals.
- The server owns official metrics and leaderboard updates.
- Long-running jobs survive worker session termination.
- Other workers can reuse findings, snapshots, artifacts, and notebook summaries.
- New worker backends can replace Codex without rewriting the server.
- New execution providers can be added without changing task logic.
- RunPod can be the first cloud execution provider without becoming the only
  cloud execution model.
- MLflow can be the first telemetry provider without becoming the official
  evaluator or leaderboard source.
- Optional provider integrations such as HF Jobs and Trackio can be added later
  without changing task logic or core architecture.
- Interactive session UX can exist without making sessions the source of truth
  for experiments, jobs, evaluations, or artifacts.
- Task-specific workflows live in task packages and skills, not in framework
  control logic.

## 16. Open Design Questions

- No pre-refactor task/artifact migration is planned for the current cleanup
  phase. Revisit only if a concrete reproducibility or benchmark-comparison need
  appears.
- What export bundle format is useful for reproducibility without constraining
  the live architecture?
- How should assignment visibility policies be expressed for islands, explorers,
  cross-pollinators, and exploiters?
- How should approval work for autonomous cloud jobs when no human is actively
  watching?
- What is the first ML-style task that is small enough to validate the new
  infrastructure without dominating the refactor?
- Should session traces be stored as first-class artifacts, or only as debugging
  attachments to WorkerSession records?
- Which telemetry interface is minimal enough to support MLflow first, then
  Trackio, TensorBoard, W&B, plain logs, and task-specific dashboards?
