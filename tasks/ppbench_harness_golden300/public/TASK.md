# PPBench General LLM Harness

Optimize a reusable PPBench pencil-puzzle harness. This is a
**harness-engineering** task: improve the Python system that constructs puzzle
context, calls the fixed LLM backend, parses/repairs model output, and returns
legal PPBench replay moves. It is not a raw URL guessing task and not a pure
hand-coded logical-solver benchmark.

The optimization target is the harness's agentic behavior. Improve prompt
construction, context shaping, model-call policy, parsing, repair, and fallback
logic. Do not hard-code puzzle answers, memorize private evaluator instances, or
replace the harness with a complete deterministic puzzle solver.

The submitted candidate must expose:

```python
def solve_puzzle(puzzle: dict, budget: dict | None = None) -> dict:
    ...
```

The harness solves one puzzle at a time. It is expected to call the configured
LLM backend and may use deterministic helper logic for prompt construction,
response parsing, move repair, caching, and fallback behavior. This task is not
a pure hand-coded logical-solver benchmark.

The candidate artifact uses a task-defined shape rooted at the workspace root.
`initial.py` is the entrypoint, and helper files next to it are included in
submitted snapshots.

## Model Access

Before running an experiment that should make model calls, export the Codex
backend variables:

```bash
export OPENAI_API_KEY=$(jq -r '.tokens.access_token' ~/.codex/auth.json)
export OPENAI_BASE_URL=https://chatgpt.com/backend-api/codex
export MODEL_NAME=gpt-5.2
```

The task contract fixes the model to `gpt-5.2`. Candidate code should use
that model and should not switch models during optimization.

The provided baseline already uses the Codex backend's required streamed
Responses API path. API transport, backend URL, model selection, and long
request timeouts are task/environment responsibilities; optimization work
should focus on harness behavior such as prompt construction, context use,
model-call policy, parsing, and repair.

Do not change the API calling stack. Keep the task-provided `pydantic_ai`
streamed `OpenAIResponsesModel` / `AsyncOpenAI` transport. Do not replace it
with hand-written `urllib`, `requests`, `httpx`, direct `openai`, or raw
`/responses` HTTP clients. The verifier rejects candidates that change this
transport policy.

## Seed Baseline

The public filesystem includes measured baseline artifacts:

- `BASELINE.md`
- `baseline_results.json`

Use these files as the fixed public control result for the seed `initial.py`;
do not spend optimization time rerunning the seed just to rediscover its score.

Recorded seed scores for this task version:

- `probe10`: 2/10 resolved, 10/10 legal, 0 invalid
- `private50`: 6/50 resolved, 50/50 legal, 0 invalid

The seed solves public `lightup` and `nurimisaki` probe instances, and solves
private `hitori`, `lightup`, `norinori`, and `nurimisaki` instances in
aggregate. This means `initial.py` is a real nonzero baseline. Candidate work
should preserve that capability and improve from it.

## Puzzle Input

The host task code passes a public-safe puzzle record:

```python
{
    "puzzle_id": str,
    "puzzle_type": str,
    "puzzlink_url": str,
    "width": int | None,
    "height": int | None,
    "metadata": dict,
    "prompt_context": dict,
}
```

`prompt_context` is the main harness input. It is generated by host-side task
code from public puzzle material and may contain:

- `official_prompt`: the benchmark-style public puzzle prompt when available
- `board_text`: a text representation of the puzzle record and encoded board
  including a PPBench/pzpr string representation when the host engine can
  construct one
- `rules_text`: public rule text for the puzzle type when bundled locally
- `coordinate_notes`: pzpr / PPBench replay coordinate conventions
- `input_examples`: public pzpr interaction examples for this puzzle type
- `move_format`: replayable move formats accepted by the evaluator

Use this context to build better model prompts and output repair logic. The
context is intentionally non-answer-bearing: it does not include decoded
solution moves, private split membership, or answer-key paths.

Do not rely on local PPBench dataset files, decoded solutions, answer keys, or
private split membership. The host-side task strips answer-bearing fields before
calling `solve_puzzle`.

## Feedback

- `ve verify` checks importability, function contract, fixed-model metadata,
  clean timeout/crash behavior, and move-trace legality on smoke cases. It is
  structural and defaults to zero model calls.
- `ve probe` runs the public `ppbench_probe10` bundle derived from PPBench
  `golden_300` and returns per-puzzle diagnostic records.
- `ve submit` always runs the full hidden `private50` evaluator over the local
  `ppbench_repr50` bundle derived from `golden_300`.
  Evaluator puzzle ids, URLs, move traces, and per-instance outcomes are
  private and are not returned to the agent.

The evaluator score is the number of private holdout puzzles solved. Full
private submits run ten puzzle instances concurrently to keep 50-instance
evaluation practical.

Do not rush to `ve submit` merely because the candidate verifies. First use
`ve probe` to check for regression against the seed baseline. A candidate below
the seed's 2/10 public `probe10` score is normally not ready for a full
private50 submit.

## Move Format

Return replayable PPBench move strings:

```text
mouse,left,x,y
mouse,right,x,y
mouse,left,x1,y1,x2,y2
mouse,leftx2,x,y
mouse,rightx2,x,y
key,1
```

An empty move list with `status="failed"` is valid. Illegal move syntax,
host-side timeouts, uncaught crashes, and malformed return payloads are invalid
outcomes.

## Local Benchmark Source

The host evaluator defaults to the task-local benchmark bundles:

- `benchmarks/ppbench_probe10` for cheap public probes
- `benchmarks/ppbench_repr50` for private evaluator scoring

Candidate workspaces must not read benchmark directories directly. The host
passes only public-safe puzzle records into `solve_puzzle`.

Host-only smoke tests may set `AO_PPBENCH_VERIFY_LIMIT`,
`AO_PPBENCH_PROBE_LIMIT`, and `AO_PPBENCH_MAX_MODEL_CALLS` to reduce cost while
checking framework plumbing.
`AO_PPBENCH_EVALUATE_LIMIT` is not part of the task policy: `ve submit` means
the full private50 evaluator for this task version.
`AO_PPBENCH_VERIFY_MODEL_CALLS` controls verify-time model calls separately;
the default is `0`. Probe and evaluator runs default to a small multi-call
budget so candidates can implement agentic repair loops when useful.
The host passes `request_timeout_s` and `preferred_reasoning_effort` in the
budget so candidates do not need to discover backend timeout policy by trial
and error. Full private submits are intentionally slow; configure the outer
runtime IPC submit timeout long enough for ten-way private50 evaluation.
Do not background long-running `ve` commands with shell `&`: wait for foreground
`verify`, `probe`, and especially `submit` calls to return so the framework can
record canonical artifacts and clean up child processes.

The provided `initial.py` is a simplified agentic baseline. It is intentionally
stronger than an always-empty stub, but it is still meant to be improved by the
optimizer rather than treated as a near-final solver.
